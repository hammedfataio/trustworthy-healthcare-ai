# Research Methodology

## Trustworthy Healthcare AI

**Methodological Framework for Reproducible Evaluation of Calibration, Uncertainty, Robustness, Distribution Shift, and Multimodal Healthcare AI**

---

## 1. Purpose

This document defines the methodological framework governing experiments in the Trustworthy Healthcare AI project.

The purpose is to ensure that experimental conclusions are based on reproducible procedures, appropriate evaluation, controlled use of validation and test data, and transparent reporting of limitations.

The methodology is designed to evolve as the project progresses from medical image classification toward uncertainty-aware, multimodal, and generative healthcare AI.

The central methodological principle is:

> **Experimental conclusions should be determined by evidence produced under a predefined evaluation procedure rather than by selectively interpreting favourable results.**

---

## 2. Research Design

The project follows an iterative empirical research design.

Each experiment begins with a research question and proceeds through:

```text
Research Question
        ↓
Hypothesis
        ↓
Experimental Design
        ↓
Data and Model Selection
        ↓
Implementation
        ↓
Validation
        ↓
Held-Out Evaluation
        ↓
Quantitative Analysis
        ↓
Critical Interpretation
        ↓
Limitations
        ↓
Next Research Question
```

Experiments are therefore connected rather than independent.

Findings from one experiment may motivate or modify subsequent experiments.

---

## 3. Experimental Protocol

Where applicable, each experiment should document:

### Research Question

The specific question being investigated.

### Hypothesis

The expected relationship or behaviour before observing the final results.

### Experimental Variables

The variables intentionally changed during the experiment.

### Controls

The factors kept constant to support meaningful comparison.

### Evaluation Criteria

The metrics and analysis procedures used to evaluate the hypothesis.

### Results

Quantitative and qualitative evidence generated by the experiment.

### Interpretation

What the evidence supports and what it does not support.

### Limitations

Factors restricting generalisation or interpretation.

### System Implication

Whether the result provides evidence for modifying or integrating a system component.

---

## 4. Dataset Strategy

The initial experimental benchmark is **PneumoniaMNIST**, part of the MedMNIST benchmark collection.

It provides a lightweight and reproducible environment for investigating trustworthiness concepts before progressing to more complex healthcare datasets.

The current task is binary classification:

**Normal vs Pneumonia**

The dataset provides predefined training, validation, and test splits.

Current split sizes are:

| Split | Samples |
|---|---:|
| Training | 4,708 |
| Validation | 524 |
| Test | 624 |
| Total | 5,856 |

The training distribution is imbalanced:

| Class | Training Samples | Approximate Share |
|---|---:|---:|
| Normal | 1,214 | 25.79% |
| Pneumonia | 3,494 | 74.21% |

This imbalance is considered when interpreting aggregate metrics.

---

## 5. Role of the Initial Benchmark

PneumoniaMNIST is not intended to represent the full complexity of real clinical deployment.

Its role is to provide a controlled environment for investigating:

- predictive performance;
- calibration;
- uncertainty;
- selective prediction;
- robustness; and
- controlled distribution shift.

Findings from this benchmark should therefore not automatically be generalised to other datasets, populations, imaging systems, or clinical environments.

Later stages should progressively introduce more challenging datasets and modalities when justified by the research question.

---

## 6. Data Partitioning

The project follows strict separation between:

**Training → Validation → Test**

### Training Set

Used for optimisation of model parameters.

### Validation Set

Used where appropriate for:

- model selection;
- hyperparameter decisions;
- calibration fitting;
- uncertainty thresholds;
- referral thresholds; and
- other experimental decisions.

### Test Set

Used for final held-out evaluation after methodological decisions have been made.

The test set should not be used to select hyperparameters, calibration parameters, uncertainty thresholds, or preferred methods.

This separation reduces test-set leakage and overly optimistic evaluation.

---

## 7. Test-Set Governance

Because repeated experimentation can gradually turn a test set into an implicit development set, the project adopts an additional principle:

> **The held-out test set should be interrogated only when the experimental procedure is sufficiently specified.**

When alternative methods are compared, method selection should be based on validation evidence wherever possible.

The test set should be used to estimate final performance of the selected procedure rather than repeatedly guide methodological decisions.

As the project becomes more complex, additional validation strategies may be introduced where appropriate.

---

## 8. Reproducibility

Experiments should record sufficient information to allow reproduction.

Where applicable, this includes:

- Python version;
- package versions;
- dependency lockfile;
- random seed;
- dataset version;
- dataset split;
- transformations;
- model architecture;
- optimiser;
- learning rate;
- batch size;
- number of epochs;
- checkpoint;
- calibration method;
- uncertainty method;
- evaluation metrics; and
- relevant experimental configuration.

The project currently uses:

- Python 3.11;
- `uv` for dependency management;
- `uv.lock` for environment locking; and
- Git for source and documentation version control.

---

## 9. Randomness and Experimental Stability

The initial experiments use a fixed random seed to improve reproducibility.

However, a single seed does not establish that an observed result is stable.

For experiments where stochastic variation could materially affect conclusions, later studies should consider:

- repeated training runs;
- multiple random seeds;
- mean performance;
- variability measures; and
- confidence intervals where appropriate.

The level of repetition should be proportionate to the research question and available computational resources.

## 10. Baseline Model

EXP-001 established a lightweight convolutional neural network.

The architecture contains:

- two convolutional blocks;
- ReLU activations;
- max pooling;
- a fully connected hidden layer; and
- a single output logit for binary classification.

Training used:

- binary cross-entropy with logits;
- Adam optimisation;
- learning rate `0.001`;
- batch size `64`;
- 10 epochs; and
- random seed `42`.

The model is intentionally simple.

Its role is to provide a controlled baseline for investigating trustworthiness rather than to maximise benchmark performance.

---

## 11. Baseline Evaluation

The baseline is evaluated using multiple metrics because class imbalance makes accuracy alone insufficient.

Current predictive metrics include:

- accuracy;
- AUROC;
- sensitivity;
- specificity;
- precision; and
- F1-score.

The confusion matrix is also inspected to understand class-specific errors.

EXP-001 produced:

| Metric | Result |
|---|---:|
| Accuracy | 0.8846 |
| AUROC | 0.9370 |
| Sensitivity | 0.9846 |
| Specificity | 0.7179 |
| Precision | 0.8533 |
| F1-score | 0.9143 |

These metrics establish predictive behaviour but do not establish trustworthy confidence.

## 12. Calibration Methodology

Calibration investigates whether predicted probabilities correspond appropriately to observed outcomes.

EXP-002 evaluates calibration using:

- reliability analysis;
- Brier score;
- Expected Calibration Error;
- confidence distributions;
- high-confidence error analysis; and
- temperature scaling.

Temperature scaling is fitted using validation logits and labels.

The held-out test set is not used to optimise the temperature parameter.

This separation is important because fitting calibration parameters directly on test data would contaminate the final evaluation.

---

## 13. Calibration Interpretation

Calibration metrics should not be interpreted in isolation.

### Expected Calibration Error

ECE provides a summary of differences between confidence and observed outcomes across probability bins.

However, ECE depends on choices such as:

- number of bins;
- binning strategy; and
- sample size.

It should therefore be interpreted alongside reliability diagrams and other metrics.

### Brier Score

The Brier score evaluates squared error between predicted probabilities and binary outcomes.

It is a proper scoring rule but reflects more than calibration alone.

It should therefore not be described as a pure calibration measure.

### Reliability Diagrams

Reliability diagrams provide a visual comparison between predicted probability and observed event frequency.

Interpretation should consider the number of samples contributing to different probability regions.

---

## 14. Current Calibration Evidence

EXP-002 fitted temperature scaling using validation data.

The learned temperature was:

**T = 1.007948**

Validation negative log-likelihood changed from:

**0.097432 → 0.097427**

This represents negligible improvement in the current experimental setting.

The appropriate conclusion is therefore limited:

> **Global temperature scaling provided negligible calibration improvement for this baseline model under the current experimental conditions.**

The result should not be generalised to temperature scaling across medical AI systems.

---

## 15. Uncertainty Quantification Methodology

EXP-003 will investigate whether explicit uncertainty estimates provide useful information about prediction reliability.

Before implementation, the experiment should define:

- the uncertainty quantity being estimated;
- the method used to estimate it;
- the expected relationship between uncertainty and error;
- the validation procedure; and
- the held-out evaluation criteria.

Potential methods may include:

- predictive entropy;
- stochastic inference;
- Monte Carlo dropout where architecturally appropriate;
- ensemble disagreement; or
- other methods justified by relevant literature.

A deterministic sigmoid probability should not automatically be treated as a complete measure of predictive uncertainty.

---

## 16. Uncertainty Evaluation

The key question is not merely:

> **Can an uncertainty score be calculated?**

It is:

> **Does the uncertainty estimate provide useful information about model failure?**

Evaluation may therefore investigate:

- uncertainty for correct vs incorrect predictions;
- ability of uncertainty to discriminate errors;
- uncertainty distributions;
- high-uncertainty error concentration;
- uncertainty under distribution shift; and
- downstream selective-prediction performance.

The exact metrics should be specified before final test evaluation.

---

## 17. Selective Prediction Methodology

Selective prediction investigates whether model reliability can improve when the system is allowed to abstain from a subset of predictions.

Conceptually:

```text
All predictions
       ↓
Rank by uncertainty / estimated risk
       ↓
Retain lower-risk predictions
       +
Refer higher-risk predictions
       ↓
Measure performance vs coverage
```

Potential evaluation includes:

- coverage;
- selective risk;
- risk-coverage curves;
- retained-case accuracy;
- retained-case sensitivity/specificity where appropriate; and
- error concentration among referred predictions.

Referral thresholds should be determined without optimising on the held-out test set.

---

## 18. Distribution-Shift Methodology

Distribution-shift experiments investigate model behaviour when evaluation data differ systematically from the original training conditions.

Where possible, shifts should be:

- explicitly defined;
- reproducible;
- clinically or technically motivated;
- parameterised; and
- evaluated at multiple severity levels when appropriate.

Evaluation should examine changes in:

- predictive performance;
- calibration;
- uncertainty;
- selective prediction;
- and failure-detection behaviour.

The objective is not merely to demonstrate that performance decreases.

The more important question is:

> **Does the system recognise that its reliability is deteriorating?**

---

## 19. Robustness Methodology

Robustness experiments will introduce controlled input perturbations appropriate to the modality.

For imaging, examples may include carefully justified changes to:

- noise;
- contrast;
- brightness;
- blur;
- resolution; or
- other acquisition-related characteristics.

Perturbations should not be selected solely because they cause model failure.

Their purpose should be stated before evaluation.

Results should be reported across perturbation levels rather than only presenting the most damaging condition.

---

## 20. Multimodal Methodology

Later research may combine medical images with structured clinical variables or text.

Multimodal experiments should distinguish between:

- unimodal baselines;
- multimodal models; and
- ablation conditions.

This is necessary to determine whether performance improvements genuinely result from multimodal information.

Potential questions include:

- Does multimodal fusion improve discrimination?
- Does it improve calibration?
- Does uncertainty become more informative?
- What happens when one modality is missing?
- What happens when modalities conflict?
- Which modality dominates the model?
- Does distribution shift in one modality affect the entire system?

---

## 21. Generative AI Methodology

Generative and vision-language models require evaluation beyond classification metrics.

Future methodology may consider:

- factual correctness;
- grounding;
- consistency with source inputs;
- hallucination or unsupported claims;
- robustness;
- uncertainty communication;
- multimodal consistency;
- response quality; and
- human evaluation where justified and appropriately designed.

Metrics and evaluation procedures should be chosen according to the specific generative task rather than imported uncritically from classification experiments.

---

## 22. Comparison Principles

When comparing methods, the project should aim to keep non-target variables constant.

For example, if comparing uncertainty methods, comparisons should avoid simultaneously changing:

- dataset;
- model architecture;
- preprocessing;
- training procedure; and
- evaluation split

unless the experimental design explicitly requires those changes.

This improves attribution of observed differences to the method being investigated.

---

## 23. Statistical Reporting

Where appropriate, future experiments should report more than point estimates.

Depending on the research question and computational feasibility, this may include:

- standard deviation across runs;
- bootstrap confidence intervals;
- confidence intervals for performance metrics;
- paired comparisons; and
- effect sizes.

Statistical tests should be used only when they address a clearly defined research question.

Statistical significance should not be treated as equivalent to clinical or practical significance.

---

## 24. Error Analysis

Aggregate metrics may hide important model behaviours.

Experiments should therefore include error analysis where relevant.

This may investigate:

- false positives;
- false negatives;
- high-confidence errors;
- high-uncertainty correct predictions;
- low-uncertainty errors;
- class-specific failures;
- shifted-input failures; and
- recurring qualitative failure patterns.

Error analysis can generate new research hypotheses but should be distinguished from confirmatory evaluation.

---

## 25. Avoiding Data Leakage

Potential sources of leakage include:

- fitting calibration parameters on test data;
- selecting thresholds using test results;
- repeatedly changing the model after inspecting test performance;
- preprocessing using information derived from the entire dataset;
- accidental overlap between splits; and
- selecting the preferred method based on final test metrics.

Experiments should explicitly consider these risks.

When a methodological decision depends on observed data, the validation set should generally be preferred.

---

## 26. Experiment Completion Criteria

An experiment is considered complete when the relevant components have been addressed:

```text
Research Question
        ↓
Hypothesis
        ↓
Method
        ↓
Implementation
        ↓
Validation
        ↓
Held-Out Evaluation
        ↓
Results
        ↓
Interpretation
        ↓
Limitations
        ↓
Artifacts
        ↓
Documentation
```

A successful code execution alone does not constitute a completed research experiment.

---

## 27. Experimental Artifacts

Where applicable, each experiment should produce:

- implementation notebook or script;
- reusable source code where appropriate;
- experimental configuration;
- saved model checkpoint where appropriate;
- metrics table;
- figures;
- experiment report;
- research-log entry; and
- Git commit documenting the completed stage.

This creates traceability between the experiment and its conclusions.

---

## 28. Current Methodological Limitations

The current research has several limitations that should remain explicit.

These include:

- relatively small benchmark data;
- low-resolution images;
- binary classification;
- a lightweight baseline architecture;
- limited evidence across random seeds;
- no external clinical validation;
- no current multimodal data;
- no current clinical workflow evaluation; and
- no evidence of deployment performance.

These limitations define opportunities for later research rather than weaknesses to conceal.

---

## 29. Research Integrity

The project follows several reporting principles.

### Evidence Before Claims

Claims should not exceed what the experiment supports.

### Negative Results Are Reportable

Negligible or negative results should be documented when methodologically meaningful.

### Planned Work Is Not Completed Work

Future components should remain clearly labelled as planned or future research.

### Limitations Are Part of the Result

Limitations should be reported alongside conclusions.

### Reproducibility Matters

A result that cannot be traced to its experimental procedure is substantially less useful.

---

## 30. Methodological Evolution

This methodology is expected to evolve as the project progresses.

The transition from:

**medical image classification**

to:

**uncertainty-aware prediction**

to:

**multimodal and generative healthcare AI**

will require increasingly sophisticated experimental designs.

New methods should therefore extend this framework rather than silently replacing earlier methodological principles.

---

## 31. Governing Principle

The methodology is ultimately guided by one question:

> **What evidence would be required to justify trusting this model behaviour?**

The project therefore evaluates not only whether an AI model performs well, but whether its confidence, uncertainty, robustness, and behaviour under changing conditions provide meaningful evidence about when its outputs may be unreliable.
